### 2026-08-19 | M1 acceptance script written; it found F11 (aliased snapshot); two job failures encoded as rules

* Wrote `scripts/research/m1_gpu_acceptance.py` while the benchmark job ran — CPU work that does not depend on the benchmark numbers, per the frozen policy.
* **It immediately found a real defect, F11.** `training_state_dict` cloned the adapter tensors but handed back the optimizer/EMA `state_dict()` payloads by reference, so continuing to train silently rewrote the "snapshot". Resume on the real U-Net diverged by **max|Δ| = 1.570e-04** across 878 trainable tensors after only 2 replayed steps. Fixed with a deep clone; resume is now **exactly 0.000e+00**.
* **The interesting part is why S3 never caught it:** S3 pickles the state through `torch.save`, and serialisation breaks the aliasing. Only an in-memory snapshot exposes it — which is what a resume test, or a training loop doing periodic in-memory checkpointing, actually does. Added **S4 SNAPSHOT-IMMUTABLE**.
* The same CPU dry run also caught a bug of mine before it could cost a job: `ema.update(unet)` where the EMA had been built on the holder, so every lookup raised `KeyError`.
* **Two GPU jobs failed, ≈0.198 credits total, both fast and both my sequencing errors:** `gpu-benchmark-1` lacked the `cd` into the repo (a job starts in `$HOME`), and `gpu-benchmark-2` was refused by its own dirty-tree preflight guard because I launched with uncommitted edits. The guards worked exactly as designed; the rules are now written down instead of remembered.
* Suite **13/13 PASS**. Still **zero GPU numbers**: `compute_budget.md` remains 100% `TBD_MEASURED`, Compute Gate CG unresolved, M3 blocked, and **M1 GPU acceptance unclaimed**.
